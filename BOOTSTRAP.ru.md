# Подключение новой машины

Эта страница — про **вторую и последующие** машины, когда хранилище уже есть и в
нём что-то лежит. Про самую первую написано в
[README](README.ru.md#быстрый-старт-первая-машина).

Скопируйте текст ниже целиком и вставьте в Claude Code на новой машине.
Требований к структуре каталогов нет: подключается и машина, где ни одного
вашего проекта ещё не лежит.

*[English version](BOOTSTRAP.md)*

## Промт для Claude Code

```
Подключи эту машину к моему общему хранилищу Claude Code. Действуй по шагам
и на каждом показывай, что получилось.

1. СНАЧАЛА обнови сам Claude Code — до всех остальных шагов:
       claude --version
       claude update
       claude doctor
   Формат транскрипта сессий меняется между релизами, поэтому машины должны
   быть на близких версиях: старая версия может не понять сессию, приехавшую
   с более свежей.

   В выводе `claude doctor` посмотри две строки и покажи их мне:
     - `Config install method:` — если не `native`, то Claude Code поставлен
       пакетным менеджером системы, и `claude update` там не работает:
       обновляй штатным для этой ОС способом (pacman/apt/brew/winget).
     - `Auto-updates:` — должно быть `enabled`. Если `disabled`, проверь, не
       задана ли переменная DISABLE_AUTOUPDATER (в окружении, в ~/.claude/settings.json
       в блоке env, в профиле шелла) — и убери её, чтобы машина обновлялась сама.

   Поле `autoUpdates` в ~/.claude.json трогать НЕ надо: для нативной установки
   оно не используется и может показывать false при работающих автообновлениях.
   Источник истины — строка `Auto-updates:` в выводе doctor.

   Покажи мне версию до и после, и продолжай только после обновления.

2. Проверь, что установлены git, gh (или чем размещено моё хранилище) и python3
   (нужен 3.9+). Чего нет — поставь штатным для этой ОС способом и скажи мне,
   что именно поставил.

3. Убедись, что git может достучаться до моего репозитория. Для GitHub это
   `gh auth status`, а после входа обязательно `gh auth setup-git`: одной
   авторизации `gh` мало — пока не прописан креденшел-хелпер, `git pull` и
   `git push` внутри движка падают с `could not read Username for
   'https://github.com'`, хотя `gh auth status` показывает исправный вход.

   Заодно проверь `git config --get user.email` и `--get user.name`: без них
   `ccsync push` не сможет сделать коммит.

4. Если Claude Code на этой машине стоял и раньше (есть ~/.claude со скиллами,
   памятью, сессиями) — СНАЧАЛА сделай архив, до любых шагов ccsync:
       tar czf ~/claude-backup-$(date +%Y%m%d).tar.gz -C ~ .claude $(cd ~ && ls .claude.json 2>/dev/null)
   (на нативном Windows — тем же `tar` из PowerShell с явной датой в имени, или
   просто копией папок). Покажи мне путь и размер архива. На чистой машине этот
   абзац пропусти.

   Клонируй моё хранилище именно по этому пути — на него ссылаются
   slash-команды:
       git clone <адрес моего репозитория> ~/claude-code-sync

5. Заведи паспорт этой машины:
       python3 ~/claude-code-sync/bin/ccsync.py init
   Идентификатор предложит сам скрипт — покажи мне предложенный вариант
   и дай подтвердить или изменить. Идентификатор должен быть понятным
   (например mac-studio, win11-laptop, ubuntu-thinkpad) и не повторять
   существующие: их список — `python3 ~/claude-code-sync/bin/ccsync.py machines`.
   В заметке к машине опиши коротко, что это за машина.

6. Токены. Если хранилище возит зашифрованные секреты (список —
   `python3 ~/claude-code-sync/bin/ccsync.py secrets`), этой машине нужен
   собственный ключ age, чтобы их расшифровать:
       age-keygen -o ~/.claude/ccsync-age.key && chmod 600 ~/.claude/ccsync-age.key
       python3 ~/claude-code-sync/bin/ccsync.py secrets add-recipient
       python3 ~/claude-code-sync/bin/ccsync.py push tools
   Затем скажи мне выполнить `/sync-pull tools` и `/sync-push tools` на машине,
   которая уже умеет расшифровывать, — так файлы перешифруются и для этой. До
   тех пор `pull` сообщает, что секреты не расшифровать, — это ожидаемо. Если
   age не установлен, сначала поставь его. Если секретов в хранилище нет, здесь
   ничего делать не надо: если на шаге 8 скрипт скажет, что какого-то секрета не
   хватает, — назови его мне, я впишу значение в ~/.claude/ccsync-secrets.env.

7. Прими состояние:
       python3 ~/claude-code-sync/bin/ccsync.py pull all
   Про непривязанные проекты скрипт спросит путь. Если проекта на этой машине
   нет — пропускай, его сессии уедут в ~/claude-sessions/<ключ> и всё равно
   будут открываться.

7а. ТОЛЬКО если Claude Code здесь стоял и раньше. Хуки синхронизации заработают
   лишь после перезапуска (шаг 10), поэтому до него отсюда ничего само не уедет —
   это окно, чтобы разобрать прежнее состояние машины. Разбирай вместе со мной,
   ничего не решай за меня:

   а) MCP-серверы: `python3 ~/claude-code-sync/bin/ccsync.py mcp`. Серверы с
      пометкой «только здесь, в хранилище ещё нет» при первом push уедут на ВСЕ
      машины. Покажи их мне; завязанные на эту машину (её пути, её программы)
      пометь до push: `ccsync.py mcp scope <имя> --here`.
   б) Скиллы и команды: сравни `ls ~/.claude/skills ~/.claude/commands` с
      `~/claude-code-sync/tools/skills` и `tools/commands`. Что есть только
      здесь — покажи мне: при push это уедет всем. Ненужное убери до push.
   в) Память. `pull` сохранил прежний индекс в MEMORY.md.bak (рядом с новым
      MEMORY.md, в ~/.claude/projects/<слаг домашнего каталога>/memory/); там же
      лежат прежние заметки-файлы. Память есть и в каталогах других проектов —
      `ls ~/.claude/projects/*/memory`. Пройди это со мной по одной заметке:
        - обо мне, моей работе, проектах: в хранилище версия свежее — переносим
          только то, чего там нет (дополняем существующий факт или новый global);
        - про эту машину (её пути, софт, настройки): новый факт со scope этой
          машины или `os:darwin` / `os:win32`;
        - устаревшее — не переносим, оно останется в архиве из шага 4.
      Новые факты — по правилам из блока ccsync в ~/.claude/CLAUDE.md.
      `ccsync adopt` для памяти здесь НЕ годится: на любой машине, кроме первой
      в хранилище, он переносит только заметки с явным scope, остальные
      перечислит — их размечаем руками.
   г) После этого: `python3 ~/claude-code-sync/bin/ccsync.py adopt` (каталоги
      skills/commands/… станут симлинками в хранилище; прежние копии — в
      ~/.claude/backups/) и `ccsync.py push all`.

8. Доложи, каких секретов не хватает (если вообще не хватает) и какие плагины
   надо доустановить — скрипт печатает готовую команду `claude plugin install ...`.

9. Проверь, что всё встало:
       python3 ~/claude-code-sync/bin/ccsync.py status
       python3 ~/claude-code-sync/bin/ccsync.py machines
       python3 ~/claude-code-sync/bin/ccsync.py mcp
   Последняя команда покажет MCP-серверы и их состояние здесь. Сервер со
   строкой «НЕ ЗАПУСТИТСЯ» либо доустанавливаем, либо помечаем как не нужный
   на этой машине: `ccsync.py mcp scope <имя> --not-here`.
   Отдельно подтверди, что в ~/.claude появились симлинки skills, commands,
   hooks, plans и что в MEMORY.md есть раздел «Про эту машину» (сначала он
   будет пустым — это нормально, факты про эту машину появятся позже).
   Сверь версию Claude Code с остальными машинами — `machines` печатает её
   для каждой, а `status` предупредит, если где-то версия новее этой.

10. Перезапусти Claude Code, чтобы подхватились хуки, и убедись, что в начале
   новой сессии печатается блок [ccsync] Машина: ...

Важно: файлы ~/.claude/ccsync-machine.json и ~/.claude/ccsync-age.key
не синхронизируются — они у каждой машины свои. Не копируй их с других машин.
~/.claude/ccsync-secrets.env ездит, только если его взяли под синхронизацию как
секрет, и тогда только зашифрованным.
```

## Что произойдёт

| Шаг | Результат |
|---|---|
| `init` | Заведёт `~/.claude/ccsync-machine.json` и зарегистрирует машину в `machines/<машина>.json` |
| `pull all` | Симлинки на скиллы/команды/хуки/планы, `CLAUDE.md` и `statusline.py` (если они есть в хранилище), `settings.json` под локальные пути, MCP-серверы, скрипты и systemd-юниты обвязки, расшифрованные секреты (если у машины есть ключ), локальный `MEMORY.md` по скоупам, транскрипты сессий |
| Хуки | `SessionStart` тянет и печатает «где ты», `Stop` и `SessionEnd` отдают |
| Проверка | `tools/tests/run-all.sh` — тестовые стенды; на свежей машине стоит прогнать, чтобы убедиться, что движок здесь работает |

## Машина, где Claude Code уже стоял

Общему хранилищу подключение такой машины не вредит: `pull` берёт из хранилища
его скиллы, `CLAUDE.md` и настройки, а первый `push` после этого отдаёт только
то, что изменилось на машине после `pull` (ровно это проверяет стенд
`tools/tests/first-join.sh`). Меняется сама машина — её прежнее сохраняется рядом:

| Что было на машине | Что станет |
|---|---|
| `CLAUDE.md`, `settings.json` | общие; прежние — `CLAUDE.md.bak`, `settings.json.bak` |
| `MEMORY.md` | собирается из общих фактов; прежний — `MEMORY.md.bak` |
| Заметки памяти | остаются на диске; в общую память — только вручную, со scope (шаг 7а) |
| Одноимённые скиллы и команды | версия новее по времени изменения — обычно из хранилища |
| Скиллы, команды, MCP, которых нет в хранилище | уезжают на все машины при первом `push` — поэтому шаг 7а |
| Старые сессии | остаются на машине; уезжает только текущая |

**Настройки.** Первый `pull` **заменит** существующий `settings.json` общим, а не
сольёт: трёхстороннему merge, который бережёт ваши локальные ключи, нужна база
для сравнения, а она появляется только со второго раза. Поэтому если на этой
машине есть настройки, которые жалко (другая модель, тема, свой хук), после
`pull` откройте `settings.json.bak`, перенесите нужное обратно в `settings.json`
и выполните `ccsync.py push tools`. Дальше настройки у машин общие, а локальные
правки переживают любой `pull`.

## Особенности по ОС

**Windows.** Поддержаны оба варианта — нативная установка и WSL, выбирайте по
тому, где лежит ваш код, а не по удобству синхронизации.

Что сделано, чтобы нативный Windows работал без оговорок:

- В хуках нет ни одной команды шелла. Все они вызывают `bin/cchook.py`, который
  сам делает таймаут, фоновый запуск и подавление ошибок средствами Python.
  Интерпретатор и путь к хранилищу подставляются под конкретную машину при `pull`
  (в шаблоне это `{{PYTHON}}` и `{{VAULT}}`), пути с пробелами кавычатся целиком.
- Настройки и MCP собираются по узлам JSON, а не подстановкой в текст: путь вида
  `C:\Users\alex` при подстановке в строку JSON дал бы невалидную
  escape-последовательность и сломал бы весь файл.
- Симлинки пробуются всегда (при Developer Mode они работают и в Windows), а где
  недоступны — используются копии, и `push` забирает из них правки обратно
  в хранилище. Так новый скилл, поставленный на такой машине, не потеряется.
- Разделители и буква диска (`D:\Projects\…`) обрабатываются при переносе сессий.
- Вывод переключается в UTF-8, иначе консоль Windows спотыкается о кириллицу.

**Когда выбрать WSL:** если на этой машине вы только общаетесь с Клодом и
правите по мелочи. Тогда `$HOME` совпадает с линуксовым, и машина ничем не
отличается от ноутбука на Ubuntu. **Когда нативно:** если здесь настоящая
разработка в IDE, а код лежит на `D:\` — из WSL он виден как `/mnt/d`, и git по
этому пути работает заметно медленнее.

**macOS.** Ключи доступа Claude Code хранит в Keychain, а не в файле, поэтому
после подключения может потребоваться отдельный вход — это нормально
и к синхронизации отношения не имеет.

## Если проект лежит по другому пути

Пути к одному проекту на разных машинах никак не связаны, поэтому соответствие
задаётся явно — один раз на машину:

```bash
cd /путь/к/проекту/на/этой/машине
python3 ~/claude-code-sync/bin/ccsync.py bind <ключ-проекта>
python3 ~/claude-code-sync/bin/ccsync.py pull session
```

Ключи проектов покажет `status`. Привязка уезжает в общее хранилище — на
остальных машинах повторять не нужно.
